In this experiment, you will bring up an end-to-end 5G network and follow an AI-assisted control loop. You will observe:

  • how a near-real-time RAN Intelligent Controller (RIC) accepts an E2 connection from a gNB;
  • how an xApp registers with that RIC and requests RAN slice-resource changes and UE release;
  • how a pre-trained ML model supports an AI-for-RAN control loop in an O-RAN-enabled network.

The main experiment explores AI/ML-driven anomaly detection and how it informs RAN slice-resource allocation and Radio Resource Control (RRC) connection-release decisions during a controlled denial-of-service (DoS) attack. The initial connection/capture exercises establish how the system works. You will then perform one Random Forest (RF) run and one heuristic run on live traffic, using the heuristic as a rule-based baseline. You start the traffic and attack yourself, follow the resulting control actions, and compare the live measurements.

The experiment uses one POWDER d430 server and simulated RF links. Reserve the server in advance and complete the exercises during that reservation.

Background#

O-RAN exposes RAN functionality through programmable interfaces and controllers. A near-RT RIC hosts or supports control applications called xApps. AI-RAN is broader: AI can optimize RAN operation, share infrastructure with RAN workloads, or support AI services through a RAN. This lab demonstrates AI for RAN control.

  • Denial-of-service (DoS) attack: An attempt to make a network or service slow or unavailable to legitimate users, often by overwhelming it with traffic.
  • Network slicing: Creating logical networks, called slices, on shared physical infrastructure, each with its own resource settings and service policies.
  • RRC connection release: Ending a UE's active radio connection to the gNB, stopping its user-data traffic until it reconnects.

Here, a detector runs in each of the two custom UPF containers. In the first run, both UPFs use the saved Random Forest [1]. In the second, both UPFs use a TCP-aware heuristic. Each method classifies live traffic as normal or anomalous and reports counts to the same xApp. The xApp applies a fixed policy to those counts; the gNB enforces the requested resource quotas. This is the deployed inference-and-control part of an AI/ML workflow: capture traffic, extract features, classify packets, report the results, and observe the network's response to control actions. The pre-trained model stays fixed during the experiment. The heuristic run provides a non-ML baseline for the same loop. The roles of classification, decision-making, and enforcement are:

Control loop
UE traffic → UPF detector (classify) → xApp (decide) → RIC/E2 agent → gNB (enforce)
                                       └──────── telnet release request ────────┘

How the attack, xApp, and heuristic work#

DoS workload. UE1 is the traffic source under test; UE2 carries legitimate traffic. The live control-loop exercise uses a bounded SYN packet flood: UE1 sends zero-payload TCP SYN packets toward the lab DN at a requested 10,000 packets/s. This creates traffic and processing pressure on the shared radio/core path. We measure whether UE2's throughput and responsiveness degrade. Requested sending rate and achieved rate can differ.

xApp policy. Each UPF reports counts of normal/anomalous classifications. The two slices are configured before traffic starts. The xApp uses their anomaly ratios to adjust nominal physical resource block (PRB) allocation ratios. A fully anomalous 30-packet window can trigger a UE release through the separate telnet path. The same xApp policy is used in both comparison arms.

What a UE release does. A successful RRC Release removes the UE's active radio connection and interrupts its end-to-end user-data path through the gNB and UPF. Releasing UE1 therefore stops delivery of its attack traffic and its legitimate traffic over that connection. Reducing a slice quota changes its resource allocation; releasing the UE disconnects its active radio path. Correlate the release request with UE/gNB logs, traffic measurements, and reachability checks, and report any reconnection.

Heuristic. The rule labels a packet anomalous when it is TCP, has a payload of at most 14 bytes, and has either SYN without ACK or RST set. It uses the existing extracted protocol, flags, and byte counts, not the known attack IP, port, or scheduled start time. This is a fixed lab baseline; a small payload alone is not enough to trigger an anomalous label.

Both the heuristic and RF report every computed window: 30-packet windows with a ten-packet step (20 packets overlap). Legitimate connection attempts or resets can still trigger false alarms. The heuristic does not flag UDP/ICMP traffic or TCP packets outside its size/flag conditions.

There are two setup operations to distinguish. SCTP establishes the transport association; E2 Setup exchanges the gNB identity and supported RAN functions over that association. The SCTP handshake has four messages:

Message Direction Purpose
INIT gNB → RIC Requests an association and proposes transport parameters
INIT-ACK RIC → gNB Returns parameters and an integrity-protected state cookie
COOKIE-ECHO gNB → RIC Returns the cookie to the RIC
COOKIE-ACK RIC → gNB Confirms that the cookie was accepted

The cookie lets the listener defer full association state until the peer returns a valid token, helping resist spoofed connection requests. SCTP setup alone does not establish that the E2 application exchange succeeded; find the E2 Setup request and response as well.

How the heuristic labels live packets#

A packet is labeled anomalous only when all three conditions hold:

  1. Its extracted protocol is TCP.
  2. Its extracted src_bytes + dst_bytes is at most 28.
  3. Its TCP flags contain SYN without ACK, or contain RST (with or without ACK).

All other packets are labeled normal by this rule. Here, src_bytes is the TCP payload length and the existing extractor sets dst_bytes = src_bytes. Thus the byte condition means TCP payload length at most 14 bytes, excluding TCP/IP headers. It is not a measurement of bytes sent in two directions.

The code retains 28 from this lab's earlier connection-record baseline; that calibration does not establish an optimal cutoff for this live TCP-only rule.

SYN initiates a TCP connection, ACK acknowledges traffic, and RST resets or rejects a connection. Our attack sends zero-payload SYN packets, which match the rule. The flag check lets ordinary short ACK packets pass, while short connection attempts and resets are classified as anomalous. For example:

Observed packet Rule's label Reason
TCP SYN, 0-byte payload Anomalous Small connection attempt without ACK
TCP ACK, 4-byte payload Normal Neither SYN without ACK nor RST
TCP SYN/ACK, 0-byte payload Normal ACK excludes the SYN condition; no RST
TCP RST/ACK, 0-byte payload Anomalous RST satisfies the flag condition even with ACK
TCP SYN, 14-byte payload Anomalous Extracted byte sum is 28, exactly the inclusive cutoff
TCP SYN, 15-byte payload Normal Extracted byte sum is 30, above the cutoff
UDP or ICMP Normal The TCP condition fails

This is a per-packet signature, not a SYN-rate meter or a tracker of completed TCP handshakes. It does not use the known attack address, port 333, or attack start time. Legitimate connection attempts and resets can therefore cause false alarms, while attacks outside this narrow signature can be missed. Keep the fixed rule throughout both measurements and record these limitations when interpreting the live results.

Each UPF aggregates its labels into a 30-packet window and sends the normal and anomalous counts over TCP port 8080. After each report, it discards the oldest ten packets, retains twenty, and waits for ten new packets to complete the next window. Reporting every window does not mean reporting at a fixed time interval: packet arrival and processing speed determine when windows complete. Mixed legitimate and attack packets can produce intermediate anomaly ratios and quota changes; a release requires the xApp to receive a fully anomalous window. Matching individual SYN packets does not guarantee an immediate release.

Interpret utilization correctly#

  • Paper alignment: Figure 7 measures CPU utilization of a UPF Docker container. We measure that resource, including the UPF and detector processes, for both UPFs. Our two conditions are AI and a heuristic; the paper's conditions are defense enabled/disabled. This is a metric-aligned extension, not an exact replication of its numerical results.
  • Container CPU: the timestamped docker stats stream reports utilization. One fully busy logical CPU is 100%, matching Docker's Linux convention; a multithreaded container can exceed 100%. The paper does not specify its normalization. CPU utilization is not a direct power or energy measurement.
  • Quotas: E2 PRB values are configured allocation policies, not the CPU utilization metric. Actual physical radio occupancy is outside this comparison.
  • Measurement scope: each UPF's CPU includes forwarding and its detector's capture/extraction/classification/logging/reporting work, not inference alone.
  • Memory: the plots use Docker CLI-reported container memory, including its cache adjustment. This is not an individual detector's resident-set size.
  • Missing values: NA or gaps mean missing measurements, not zero load or zero latency. RTT describes received replies; always also report packet loss.
